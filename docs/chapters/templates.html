Templates

The sixteen templates below are starting points to copy and edit. A, C, E, F, L, M and N work with any tool, and O works with any repository on GitHub. B, G and I are skills, stored as a SKILL.md file, a format that Claude Code, Codex and Gemini CLI all read, so they should need little change, except that B hands its checking step to the subagent in D. J and K are skills that also use Claude Code settings, such as disable-model-invocation, which other tools may not accept. D defines a subagent with Claude Code’s settings, such as the list of tools it may use, and H combines a skill with two such subagents; both need rewriting for another tool, as does the Claude Code hook in P. None has been tested on a live module, so run each on a small example first. Each is also a file in the templates/ folder of the repository.

A. Module instruction file

Save as MODULE.md, or under the name your agent reads at the start of every session: CLAUDE.md in Claude Code, AGENTS.md in Codex, GEMINI.md in Gemini CLI.

# ECN000 Module Title

## Module facts
Level 6, 15 credits, about 120 students. Prerequisites: ECN000, ECN000.

## Learning outcomes
1. ...
2. ...

## What students know
Assume: linear algebra to eigenvalues, OLS, basic Python (pandas, numpy).
Do not assume: maximum likelihood, matrix calculus, any R or Stata.

## Notation
Returns r_t, excess returns r^e_t. Vectors bold lower case, matrices bold upper case.
Estimators carry a hat. Follow the conventions of [textbook], chapters [x-y].

## Software
Python 3.12. Packages pinned in requirements.txt. No other packages.

## House style
British spelling. Lecture notes in LaTeX using lectures/template.tex.
One lecture is 100 minutes: at most 25 slides and two worked examples.

## Rules
- Never edit anything in sources/.
- Never supply a reference, fact or number that is not in sources/ or code output.
  If something is missing, stop and list it.
- Every number in a solution comes from a script that has been run.
- Compile or run every file before reporting it finished.
- No student work or personal data is stored in this folder.

## Decisions log
2026-11-26  Dropped the Kalman filter lecture; replaced by a second GMM lab.

B. Problem-set skill

Save as .claude/skills/problem-set/SKILL.md, with the checker from template D in .claude/agents/. Run with /problem-set week05.

---
name: problem-set
description: Draft a problem set with verified solutions for one week of the module.
---

Write a problem set for $ARGUMENTS.

1. Read CLAUDE.md, the lecture notes for that week, and two past problem sets
   in problem-sets/ as the standard for style and difficulty.
2. Propose a one-page plan: each question, the outcome it tests, the expected
   time, and whether it is mechanical, applied or stretch. Wait for approval.
3. Write questions.tex, solutions.tex and solve.py in a new folder.
4. Run solve.py. Take every number in solutions.tex from its output.
5. For derivations, verify each final expression symbolically or numerically.
6. Compile both .tex files and fix any errors.
7. Use the checker subagent on the new folder: it solves questions.tex
   without seeing solutions.tex, then compares. Do not change a solution
   to match the checker; list every disagreement for me to resolve.
8. Report: what was produced, what was verified and how, every disagreement
   the checker found, and anything you could not verify. List the stretch
   questions so that I can attempt them myself.

Do not reuse or paraphrase questions from textbooks in sources/.

- the two most important improvements, each tied to a rubric criterion;
- one concrete step for the next assessment.

Use only what is in my notes. Do not add observations of your own.

D. Independent checker

Save as .claude/agents/checker.md.

---
name: checker
description: Independently solves a problem set from the questions alone and reports disagreements with the official solutions. Use before any solutions are released.
tools: Read, Grep, Glob
---

You are checking a problem set for a university module.

1. Read the questions file only. Do not open the solutions yet.
2. Solve every question yourself. You cannot run code: where a number requires
   computation, write the code in your report and mark the number as unconfirmed.
3. Only then read the official solutions.
4. For each question report: agree, or disagree with both answers and the
   likely source of the difference.
5. Separately list any question that is ambiguous, answerable without the
   intended method, or harder than its stated level.

You do not edit files or run code. You report.

E. Student-facing AI statement

Use of AI tools in ECN000

Problem sets (not assessed): any use is permitted. You will learn more by
attempting each question before asking a tool.

Coursework (40%): you may use AI tools to debug code and to check grammar.
You may not use them to write the interpretation of results or the conclusion.
Add a short declaration at the end of your submission naming any tool used
and what you used it for. You are responsible for everything you submit,
including errors and references introduced by a tool. You may be asked to
explain your submission in person.

Exam (60%): invigilated, no AI tools.

The university provides [tool] to all students at no cost. No assessment in
this module requires a paid subscription.

How AI was used in preparing this module: lecture notes and problem sets were
drafted with an AI coding agent from my own notes and checked by me. All
marks are set by the teaching team. [State any use in feedback.]

G. A written standard as a skill

Save as .claude/skills/lecture-style/SKILL.md, with more pairs of examples in examples.md in the same folder (a placeholder version is in the repository’s templates/ folder). The rules shown are placeholders, to be replaced with your own (chapter 13).

---
name: lecture-style
description: House style for lecture notes and slides in my modules. Use when writing or reviewing any teaching material.
---

## Rules
1. One idea per slide. A slide has a title that states the point, not the topic.
2. Paragraphs in notes are at most four sentences.
3. Every equation that is used later is numbered; no others are.
4. A new symbol is defined in the sentence where it first appears.
5. Each result is followed by one sentence of interpretation in plain words.
6. Worked examples use real data and state the source and sample period.

## Do not
- Open a section by announcing what it will do.
- Use rhetorical questions as slide titles.
- Use: "it is important to note", "delve", "crucial", "in today's world".

## Examples
Breaks rule 1:   title "Fama-MacBeth regressions"
Corrected:       title "Fama-MacBeth: estimate the price of risk period by period"
(more pairs in examples.md)

## When reviewing
Do not rewrite. Report each finding as:
  file and location | rule number | what is wrong | suggested fix
Finish with a count of findings per rule.

H. Assessment loop: setter, candidate, examiner

Three files make up the system in chapter 15. It is untested, so run it first on a short problem set with a round limit of two.

Save as .claude/agents/candidate.md:

---
name: candidate
description: Attempts an assessment exactly as a student would, from the student-facing files only.
omitClaudeMd: true
---

You are a student taking this module. You have been given a folder containing
the assessment brief and any data. Read only the files in that folder.

Complete the assessment in full and save your submission in the folder.
Work as a capable student would with the tools available: write and run code
where needed, and check your own work once before submitting.

Do not look for a rubric, marking notes or solutions. Do not ask questions.
When finished, list any wording you found ambiguous.

Save as .claude/agents/examiner.md:

---
name: examiner
description: Marks one anonymous submission against a rubric, criterion by criterion.
tools: Read, Grep, Glob
---

You are marking one anonymous submission. You are given the submission and
the rubric. Assume nothing about who wrote it.

For each criterion give: a mark, the band, and one sentence quoting or
pointing to the evidence in the submission. You cannot run code: check each
reported number against the code output saved in the submission, list any
number you cannot confirm this way, and do not award marks for it.

Then give the total, and list the two criteria on which the submission was
strongest. Report any place where the rubric gave you no guidance.
You do not edit files or run code.

Save as .claude/skills/assessment-loop/SKILL.md. Run with /assessment-loop assessment/coursework1.

---
name: assessment-loop
description: Iteratively tests and revises an assessment using a candidate and an examiner subagent.
disable-model-invocation: true
---

You are the setter for the assessment in $ARGUMENTS.

Settings (edit before running):
  stop when the candidate's total is below 50, or after 3 rounds,
  or when no revision satisfies the constraints.

Constraints on every revision:
  - every learning outcome in CLAUDE.md that the original assessed is still assessed
  - format, weighting, word limit and time allowance unchanged
  - a well-prepared student can complete it using only what the module taught
  - no trick wording and no reliance on information students cannot obtain

Each round:
  1. Copy the student-facing files to rounds/roundN/student/.
  2. Use the candidate subagent on that folder only.
  3. Use the examiner subagent on the submission and the rubric.
  4. Save the examiner's report to rounds/roundN/report.md.
  5. Check the stopping rule. If met, go to the final report.
  6. Identify the criteria passed most easily. Propose one or two revisions
     that satisfy every constraint. Record each in changes.md with the
     criterion it targets and the reason. Apply them to a new version.

Final report (report.md): original and final versions, the change log,
marks by criterion for every round, the final attempt in full, and which
constraints came under strain. State plainly if the format could not be
made robust.

Never edit the original assessment files. Work on copies.

J. Annual update

The year-to-year update from chapter 5. Save as .claude/skills/annual-update/SKILL.md. Run with /annual-update 2027-28.

---
name: annual-update
description: Prepare the module for a new academic year. Finds dated material, reruns figure and solution scripts on current data, and reports every change against last year. Use once a year before teaching starts.
disable-model-invocation: true
argument-hint: "[academic year, e.g. 2027-28]"
---

Prepare the module for the academic year $ARGUMENTS.

1. Read CLAUDE.md, including the decisions log.
2. List everything that has dated, with file and location: data ending in
   an old year, superseded references, examples overtaken by events, dates
   and deadlines in admin/. Change nothing yet.
3. Wait for me to mark which items to update.
4. If the folder is under version control, commit its current state first.
5. Rerun every figure and solution script on current data. Record the
   download date of each dataset next to it.
6. Where a rerun changes a number in the notes, slides or solutions, take
   the new number from the output and list the change.
7. Make the other approved updates.
8. Compile or run every changed file and fix any errors.
9. Report: each change against last year's version, file by file; every
   number that changed, old and new; anything you could not update.

Never edit sources/. Do not change learning outcomes or assessment
weightings: list any that look out of date for me to raise at module review.

K. Notebook release

The release checks from chapter 6, with the mechanical part in a script (chapter 12). Save as .claude/skills/notebook-release/SKILL.md, with the script scripts/release.py from the repository’s templates/ folder in the same skill folder. Mark solution cells with the tag solution in Jupyter. The script needs Jupyter installed in the module’s environment. Run with /notebook-release problem-sets/ps3/ps3.ipynb.

---
name: notebook-release
description: Check that a solution notebook runs from top to bottom and produce the student version without the solution cells. Use before releasing any notebook to students.
disable-model-invocation: true
argument-hint: "[path to the solution notebook]"
allowed-tools: Bash(${CLAUDE_SKILL_DIR}/scripts/release.py *)
---

Release the notebook $ARGUMENTS.

1. Check that the installed package versions match the pinned versions in
   the module (requirements.txt or its equivalent in CLAUDE.md). Report any
   difference and stop.
2. Run ${CLAUDE_SKILL_DIR}/scripts/release.py on the notebook. The script
   runs the notebook in a fresh kernel and stops at the first error. If it
   ran, it writes NAME-student.ipynb next to it, without the cells tagged
   "solution" and with all outputs cleared.
3. If the run fails, report the cell and the error. Do not edit the
   notebook to make it pass without telling me exactly what you changed.
4. Read the student version. Check that every question still makes sense
   without the removed cells, and that no answer survives in a markdown cell
   or a comment.
5. Report: whether the notebook ran and how long it took, which cells were
   removed, and anything in the student version that needs my attention.

Never release a student version from a notebook that did not run.

N. First commit

A prompt that puts a module folder under version control (chapter 4), with a check of what goes in before anything is recorded.

This folder is a teaching module that is not yet under version control.

1. Check that Git is installed and tell me which version. If it is not
   installed, stop and tell me how to install it on this computer. Do not
   install it yourself.
2. If there is no .gitignore file, create one from the module template's
   .gitignore and show it to me.
3. List every file the first commit would include, grouped by folder.
   Flag anything that looks like student work, marks, an unreleased exam,
   licensed data, or a password or key. Wait for my approval.
4. Initialise the repository and make the first commit, with the message
   "Module as of [today's date]".
5. Explain briefly what you did and how I can undo a change later.

Do not create a GitHub repository and do not push anything. I will do that
myself.

O. Checks on every change

The GitHub Actions workflow from chapter 14. It compiles every LaTeX document and runs every notebook in lectures/ and problem-sets/, and needs a requirements.txt listing the module’s Python packages. Save as .github/workflows/module-checks.yml.

# Save as .github/workflows/module-checks.yml in the module repository.
# On every push to main and every pull request, it compiles each LaTeX file
# that contains \documentclass and runs each notebook from top to bottom,
# in lectures/ and problem-sets/. Untested on a live module. If GitHub
# reports an action version below as out of date, update it.
name: Module checks

on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:

permissions:
  contents: read

jobs:
  latex:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install LaTeX
        run: |
          sudo apt-get update
          sudo apt-get install -y --no-install-recommends \
            texlive-latex-recommended texlive-latex-extra \
            texlive-fonts-recommended latexmk
      - name: Compile every document
        run: |
          status=0
          while IFS= read -r -d '' f; do
            grep -q '\\documentclass' "$f" || continue
            echo "::group::$f"
            if ! (cd "$(dirname "$f")" && latexmk -pdf -interaction=nonstopmode -halt-on-error "$(basename "$f")"); then
              echo "::error file=$f::did not compile"
              status=1
            fi
            echo "::endgroup::"
          done < <(find lectures problem-sets -name '*.tex' -print0 2>/dev/null)
          exit $status

  notebooks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - name: Install the pinned packages
        run: |
          if [ -f requirements.txt ]; then pip install -r requirements.txt; fi
          pip install nbconvert ipykernel
      - name: Run every notebook from top to bottom
        run: |
          status=0
          while IFS= read -r -d '' nb; do
            echo "::group::$nb"
            if ! jupyter nbconvert --to notebook --execute --output-dir "$RUNNER_TEMP/executed" "$nb"; then
              echo "::error file=$nb::did not run"
              status=1
            fi
            echo "::endgroup::"
          done < <(find lectures problem-sets -name '*.ipynb' -not -name '*-student.ipynb' -not -path '*/.ipynb_checkpoints/*' -print0 2>/dev/null)
          exit $status

P. A hook that protects sources/

The hook from chapter 14, for Claude Code. Save the script as .claude/hooks/protect-sources.py (it is in the repository’s templates/ folder), and add the settings below to .claude/settings.json. The deny rule covers the editing tools and the shell commands Claude Code recognises, and the hook gives the agent a clear reason when it blocks an edit. Neither stops a script the agent runs from writing into the folder, so make sources/ read-only on your computer as well.

{
  "permissions": {
    "deny": ["Edit(/sources/**)"]
  },
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write|NotebookEdit",
        "hooks": [
          {
            "type": "command",
            "command": "python3 \"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-sources.py"
          }
        ]
      }
    ]
  }
}
