14  Automation

Once a module is on GitHub (chapter 4), checks and agents can run without you starting them. Each one runs on someone else’s servers, so the rules in chapter 10 apply, and each one uses time, money or a usage allowance.

Checks on every change. GitHub Actions runs the steps in a workflow file, kept in the repository’s .github/workflows/ folder, whenever the repository changes. For a module, the useful steps are the ones on the release checklist in chapter 9 that a machine can do: compiling every LaTeX file, and running every notebook from top to bottom in a clean environment. A failure is reported against the change that caused it, so a broken notebook is found on the day it breaks. Template O is a workflow for both checks.

Standard runners are free in public repositories. Private repositories get a monthly allowance expressed in money, $12 on the free plan and $18 on Pro, which at GitHub’s published Linux rate is roughly 2,000 and 3,000 minutes (Actions billing). Check the usage page after the first week of term to see how much of it the module’s checks take.

Rules the agent cannot skip. The instruction file states rules but does not enforce them (chapter 3). A hook is a short script that runs at a fixed point, for example just before the agent edits a file, and a hook that runs before an action can block it. Hooks suit rules that must hold every time, such as no edits to sources/, no file written that contains a student number, or a compile check after every edit to a .tex file. Template P blocks edits to sources/ and pairs the hook with a permission deny rule.

Neither a hook nor a deny rule stops every route to a file. A script the agent runs, such as a Python program that writes its output into the folder, is outside both. Where a folder must not change at all, make it read-only on your computer as well.

In Claude Code. A PreToolUse hook runs before a tool call and can block it, by exiting with code 2 or by returning a deny decision. A PostToolUse hook runs after the call and cannot undo it. Hooks are set in .claude/settings.json, which is committed with the module, in .claude/settings.local.json for yourself only, or in ~/.claude/settings.json for all your projects (hooks guide).

An Edit deny rule covers all the built-in tools that edit files. It also covers shell commands that Claude Code recognises, such as sed and output redirection, but not arbitrary scripts (permissions).

Agents started from GitHub. With an integration installed, a comment that mentions the agent in an issue or a pull request starts it on the repository, and it pushes its changes for review. An erratum reported as an issue (chapter 4) can then be fixed by the agent and checked by you before the change is accepted. The work runs on GitHub’s servers and uses both the Actions allowance and the agent’s own usage. Give the integration only the permissions it needs, and read every change before accepting it.

In Claude Code. The integration is installed with /install-github-app, which needs admin access to the repository and works only with repositories on github.com. It authenticates with an API key, or with a subscription token on Pro, Max, Ultra, Team and Enterprise plans. The documentation warns never to commit either to the repository (GitHub Actions).

Sessions that run while your computer is off. A cloud session works on a copy of the repository on the provider’s servers and pushes its changes to a branch for you to review. A scheduled task runs on a timetable, for example to refresh the data behind the figures every Monday or to check every reference link two weeks before term. Both need the module on GitHub. Both also send its contents to outside servers, so no repository they can read should contain student work.

In Claude Code. Cloud sessions need GitHub to copy the repository and open pull requests. They are available on Pro, Max, Ultra and Team plans, and on Enterprise with qualifying seats (on the web). Scheduled tasks are available on Pro, Max, Ultra, Team and Enterprise plans and put their changes on branches whose names begin claude/. They were described as a research preview when this chapter was written (scheduled tasks).

Deciding what to automate.

  • Automate checks freely, since they report and change nothing.
  • Automate changes only where each one arrives as a pull request that you review.
  • Never automate anything that reads or changes student work or marks.
  • Record each automation in the instruction file’s decisions log, with what triggers it and what it may change, so that a successor knows what runs.

By field. Modules built on data gain most from scheduled refreshes, and modules with many notebooks from checks on every change. For a theory module, compiling every document on each change is usually enough.
